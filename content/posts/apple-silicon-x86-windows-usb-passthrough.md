## 起因

手上一个加密 U 盘，厂商只提供 Windows 客户端：插上后要先运行盘里的程序、输密码，加密区才会挂出来。而我的电脑是 Apple Silicon 的 Mac。

思路很直接：用 [UTM](https://mac.getutm.app/) 起一台 x86 Windows 虚拟机，把 U 盘**直通**进去，在里面解锁，再把文件传回 Mac。技术上每一块都是成熟的，我以为一个小时能搞定。

结果花了两天。这篇把坑记下来——**不写代码，只讲现象、原因和实测数字**。

## 一、先认清天花板：为什么注定慢

这件事的前提很残酷：**Apple Silicon 是 ARM，而这个客户端只能跑在 x86 Windows 上。**

在 M 系列芯片上跑 x86 系统，所有虚拟化方案都帮不上忙——Parallels、VMware 在 Apple Silicon 上**根本不支持 x86 Windows**，它们只能跑 ARM 版。UTM 是少数还提供 x86 模拟的，代价是走 QEMU 的 TCG：**把每一条 x86 指令翻译成 ARM 指令再执行**，没有任何硬件加速。

实测 CPU 全程顶在 100%，而且只能用一个核。

### 单核不是偷懒，是正确性

我一度想加核心数提速，查下来这条路走不通：**x86 是强内存序（TSO），ARM 是弱内存序**。在 ARM 上模拟多核 x86，必须在几乎每次内存访问处插入屏障指令，不但更慢，而且 QEMU 的多线程 TCG 对 x86-on-ARM 支持并不完善。

这不是理论担忧——我前一天就栽过：多核配置下虚拟机输入卡死、Windows 安装直接损坏，改回单核才救回来。10 个核在这里帮不上忙，**不是没给它用，是这种模拟方式无法安全并行**。

## 二、USB 直通：「连上了」和「能用」是两回事

这是最耗时间的一块。

### 假连接

现象：点连接，工具说成功，Windows 里什么也没有。

查下来是这样：同一只盘反复插拔后，UTM 会留下一条**失效的「已连接」记录**。你再点连接，它回一句 `Cannot connect an already connected usb device` 就结束了，而 Windows 那边其实什么都没收到。

解法是撞上这个错误时，先真正 `disconnect`，等一秒，再 `connect`。实测这样才能让 Windows 重新枚举出设备，大约 10 秒后盘符出现。

有个细节值得一提：一开始我靠匹配错误文本里的 `already connected` 来判断。后来改成了**任何连接失败都走一次重连、重试仍失败才报原始错误**——依赖英文提示语太脆，换个界面语言就失效。

### 时机：虚拟机起来 ≠ 系统起来

更隐蔽的坑在这里。

**虚拟机一启动，UTM 就会自动去抢上次连过的 USB 设备**，不需要你点任何按钮。但那一刻 Windows 内核还没起来，枚举必然失败——然后就卡死在「UTM 说连上了、Windows 里没有」的状态。

所以正确顺序是：**先让 Windows 完全进入桌面，再触发一次连接**。

### 我试图把这一步自动化，然后翻车了

「等进桌面再点一次」这个操作很烦，我想自动化掉。观察到 CPU 曲线有个非常干净的拐点：

```
[00:28] 100.0%    ← 启动中
[00:58] 100.7%
[01:08]   7.2%    ← 我判定"桌面就绪"
[01:28]   6.8%
```

于是写了段逻辑：CPU 掉到 30% 以下、连续两次达标就自动重连。

第二次运行立刻被打脸：CPU 在 54 秒就掉到 8.3%，之后 100 多秒都在 7~16% 徘徊，**而 Windows 还停在"正在启动"的画面**。我的代码在系统启动到一半时去断开重连 USB，把 usbredir 的连接打断了，虚拟机弹出 `usbredir protocol parse error`。

根因很朴素：**低 CPU 只说明它在等 I/O，不等于桌面就绪**。而且这台机器有登录密码——系统停在登录框等你输密码时当然也是空闲的，从宿主机这边**根本区分不了「在等你登录」和「已经进桌面」**。

代码撤了，注释里写清楚了原因。教训写成一句话就是：**找到一个相关性很强的信号，不等于找到了因果**。我只采样了一次就当成规律，第二次运行就证伪了，还造成了用户可见的故障。

### 还有一个更底层的：设备会自己消失

USB 3.0 的设备在直通释放后，可能**整个从系统里消失**——Finder、磁盘工具都看不到它。这是 macOS 无法对 SuperSpeed 设备做正确硬件复位导致的，UTM 官方文档也明确警告过。

唯一的恢复办法是**物理拔下重插**。这不是 bug，是这套方案的固有限制，只能写进说明里让人心里有数。

## 三、传文件：那根管子太细了

虚拟机和宿主机之间靠共享目录传文件，UTM 在 Windows 客户机上走的是 WebDAV。能用，但有两个问题。

### 单文件 47.7MB 上限

复制稍大的文件报 `错误 0x800700DF: 文件大小超出允许的限制`。

这是 **Windows 自己的默认值**：WebDAV 客户端的单文件上限写死在注册表里，默认约 47.7MB。可以改到 4GB 并重启 WebClient 服务——但这只解决了"能不能"，没解决"快不快"。

### 264 KB/s

真正劝退的是速度。实测拿同一批文件对比：

| 路径 | 速度 |
|---|---|
| U 盘 → 虚拟机本地磁盘 | **2.22 MB/s** |
| U 盘 → WebDAV 共享 | **264 KB/s** |

**差 8.6 倍**，说明 WebDAV 这层协议本身就是主要瓶颈——它的每次请求往返都要吃 CPU，而 CPU 正被指令翻译占满。

按这个速度，1.6GB 要传**将近两小时**。

### 换条路：把文件做成一张光盘

既然管子细，就别用管子。**把要传的文件做成一个光盘镜像，直接挂到虚拟机的光驱上**——虚拟机读光驱就是读宿主机硬盘，走的是本地 I/O，完全绕开 WebDAV。

macOS 自带 `hdiutil` 就能做，选 UDF 格式（ISO 9660 对大文件和中文名都不友好）。

实测数字很好看：

| | 1.68 GB 的一批文件 |
|---|---|
| 走 WebDAV 共享 | 约 1 小时 45 分钟 |
| 做成光盘镜像 | **十几秒** |

另外还有个意外收获：`hdiutil` 做镜像时会自动把 `.DS_Store` 排除掉。

代价是换光盘要在虚拟机关机状态下做——就像真电脑不能一边开机一边换光驱。为此我加了个小设计：如果虚拟机正开着，就先把盘做好记下来，**下次启动时自动挂上**，免得为换张盘专门关一次机。

**但必须说清楚**：光盘只解决了"文件进虚拟机"这一段。**"从虚拟机写进 U 盘"那一段走的还是 USB 直通，任何方案都绕不开**。如果 U 盘读写本身就慢（我这里是 2.22 MB/s），总时间还是被它卡着。

## 四、跨平台的细节：文件名和元数据

两个系统的历史包袱在这里集中爆发。

### Windows 打的包，Mac 解不开

想用「打包成一个压缩包再传」来减少往返次数，结果解压直接报错：

```
checkdir error: cannot create .../2026-?1?-??+???+-
                Illegal byte sequence
```

原因：**Windows 自带的「压缩(zipped)文件夹」用 GBK 编码存中文文件名**，而 macOS 的 `unzip`（Info-ZIP）认死 UTF-8，中文名直接变成非法字节，目录都建不出来。解出 0 个文件。

试了三条路：

| 方案 | 结果 |
|---|---|
| `unzip -O GBK` | ❌ Apple 的构建里没这个选项 |
| **`ditto -x -k`** | ✅ macOS 自带，中文名完全正确 |
| Python 手动按 GBK 解码 | ✅ 可行，但代码繁琐 |

`ditto` 胜出，一行搞定。

### Mac 打的包，Windows 里多出一堆东西

反方向同样有问题。Mac 压缩出来的包，在 Windows 里解开会多出：

- `.DS_Store` —— 记录 Finder 里图标位置的
- `._文件名` —— 存扩展属性（比如文件从哪下载的）
- `__MACOSX/` —— 整整一棵影子目录树

这些是 macOS 的元数据，它自己隐藏得好好的，Windows 不认识就全摊出来了。

实测三种打包方式在 Windows 视角下的产物：

| 方式 | Windows 里会看到 |
|---|---|
| `ditto -c -k --sequesterRsrc` | `__MACOSX/` + `._` 双档 + `.DS_Store`，**最脏** |
| Finder 右键「压缩」 | `.DS_Store` + `._` 文件 |
| `zip -X` 配合排除规则 | **只有真实文件** |

### 顺手踩的一个：`FileManager` 看不见 `._` 文件

写清理逻辑时遇到怪事：`.DS_Store` 删掉了，`._报告.docx` 纹丝不动。

原因是 **macOS 把 `._` 开头的 AppleDouble 文件当作主文件扩展属性的载体，对目录枚举透明隐藏**——`FileManager` 的枚举器根本不报告它们的存在。

绕到 `find` 这一层才清得掉。

## 五、几个"想当然"的教训

除了上面 CPU 那次，还有几个值得记：

**官方 API 不一定工作。** 启动虚拟机我一直用 UTM 的 `utm://` URL scheme，某天才发现它**根本不启动虚拟机**——打开 URL 后 30 秒，虚拟机状态仍是 stopped，进程都没出现。换成 UTM 自带的命令行工具，5 秒就起来了。这个功能很可能一直是坏的，只是我排障时都在用命令行手动启动，没走到它。

**别在界面上干等。** 有个版本点一下按钮界面会转圈快两分钟。我逐项测量了所有可疑环节——都是毫秒级。真凶是代码里一个"等虚拟机启动完成"的轮询循环，最多空等 30 秒，期间所有按钮禁用。而这个等待**毫无意义**：反正后面还要用户手动触发一次。去掉之后，从点击到界面可用只要 6 秒。

**状态要诚实。** 界面上有个"共享已验证"的绿灯，一直亮着。实际上它只检查了一个标记文件存不存在，而那个文件是**上一次会话**留下的——这次的共享其实早断了，虚拟机里那个网络驱动器显示"脱机"、目录空空如也，绿灯还亮着骗人。改成"标记文件必须写在本次开机之后"才算数，它才开始说实话。

**改完要验证发布物，不只是源码。** 中间有次我把一个已经验证过的修复，用没打补丁的源码重新编译覆盖了——用二进制里的字符串对比才查出来。源码对不等于用户手上那份对。

## 结论

这套方案现在能用，但它的上限很清楚：

- 几十 MB 的文档表格 → 感觉不到慢
- 几百 MB → 一两分钟
- 1~2 GB → 十几分钟（走光盘），这已经是最好情况

**根因始终是"在 ARM 上翻译 x86"**，配置怎么调都绕不开。真正能突破的只有让操作系统本身跑原生 ARM——要么 Windows 11 ARM 靠内置的 x86 模拟层跑那一个客户端，要么找一个有 ARM64 版客户端的 Linux 发行版。那样被翻译的就只剩一个进程，而不是整个操作系统。

不过话说回来，**一个两天的折腾，换来一台一直用不了的设备变得可用**，这笔账是划算的。何况路上这些坑，比结果本身有意思。
