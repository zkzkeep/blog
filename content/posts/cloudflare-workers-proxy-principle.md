我原来有两台境外 VPS，后来只剩一台。在今天这个大环境下，**单点就是不保险**：哪天这台机器的 IP 被封，全家就断网。

网上流传着一种「Cloudflare 免费搭 VPN」的方法：不用买服务器，在 Cloudflare Workers 上跑一段脚本就能翻墙。我照着搭了一条，当作家里 Apple TV 看视频的备用线路。

搭起来不难，难的是**弄懂它为什么能用**。不懂原理，出了问题只能瞎试；懂了原理，哪里慢、哪里不稳、哪里有风险，心里都有数。这篇文章把原理拆开讲清楚，最后附上我踩过的坑和几条使用边界。

> 文中域名、IP、UUID 均为占位符，请替换成你自己的。

## 一、先弄清楚「墙」是怎么拦的

在国内直接打开 YouTube，防火墙（GFW）主要用三招拦你：

1. **DNS 污染**：你问「youtube.com 在哪」，它抢先回你一个假地址；
2. **封 IP**：YouTube 服务器的真实 IP 直接不给通；
3. **看 SNI**：HTTPS 握手时有个**明文**字段叫 SNI，写着「我要访问 youtube.com」，它看到就掐断。

所以任何翻墙方案，本质上都在解决一件事：**让防火墙看到的东西，既不是被封的 IP，也不是被封的域名，而且看起来像一次正常的上网行为。**

## 二、为什么偏偏是 Cloudflare

Cloudflare 是全球最大的 CDN，大约**五分之一的网站**挂在它上面，其中不乏国内外企业的正常业务。几百万个网站共用它那几段 IP。

如果防火墙把 Cloudflare 的 IP 全封了，会误伤一大片正常网站，代价太大。所以**Cloudflare 的 IP 在国内基本是通的**，只是经常绕路、慢一点。

这是整个方案的地基：**找一个「封不起」的平台，躲在它后面。**

## 三、Workers 是什么，它干了什么

Cloudflare Workers 是一个「在 Cloudflare 全球机房里跑你自己代码」的服务。关键在于，它允许代码**主动向外建立 TCP 连接**（`connect()` 接口）。有了这个能力，几千行脚本就能扮演一台代理服务器。社区里最流行的实现是开源项目 edgetunnel。

一次完整的访问是这样走的：

```
 手机 / 电视                              Cloudflare 机房                    目标网站
┌───────────────┐   ① HTTPS 连接        ┌──────────────────┐   ③ 普通 TCP    ┌──────────┐
│ 代理客户端     │ ────────────────────► │ 你的 Worker       │ ──────────────► │ YouTube  │
│ 把「我要去     │   目标 IP：CF 的 IP     │ ② 拆包、核对 UUID  │                 │          │
│ YouTube」装进  │   SNI：你的小域名       │   读出真正目的地    │ ◄────────────── │          │
│ 加密信封       │ ◄──────────────────── │ ④ 把数据原路送回   │                 └──────────┘
└───────────────┘                       └──────────────────┘
        ▲
   防火墙只看到：有人在用 HTTPS 访问一个挂在 Cloudflare 上的普通小网站
```

分步说：

- **① 装信封**：客户端把「我要访问 YouTube」这个请求用 **VLESS 协议**写好，塞进 **WebSocket**，外面再套一层 **TLS 加密**（也就是 HTTPS），发给你自己的域名（比如 `proxy.example.com`）。防火墙能看到的只有：目标 IP 是 Cloudflare 的，SNI 是一个不知名的小域名，内容全是加密的。**跟打开一个普通网站没区别。**
- **② 拆信封**：Cloudflare 收到后，按域名把请求交给你的 Worker。Worker 解开 VLESS 头，先**核对 UUID**，这就是你的钥匙，不对就拒绝，所以别人扫到你的域名也用不了。然后读出真正的目的地：youtube.com。
- **③ 替你出门**：Worker 在 Cloudflare 机房里向 YouTube 发起连接。这一段在墙外，畅通无阻。
- **④ 原路返回**：YouTube 的数据经 Worker 塞回那条 WebSocket，加密送回你家。

所以 YouTube 看到的访问者是 **Cloudflare 机房的 IP**，不是你。测出口 IP 时，归属显示的是「Cloudflare」。

## 四、「优选 IP」是什么，为什么能选出香港、日本

这是整套方案里最巧妙的一环。

**Cloudflare 用的是 Anycast（任播）**：同一个 IP 在全球几百个机房同时挂着，你的数据会被网络路由送到「离你最近」的机房。但国内三大运营商的普通线路和 Cloudflare 对接很差，**从国内出去通常会被绕到美国西海岸**。我在家宽上测，默认落在美国圣何塞机房。

另一个事实：**Cloudflare 的任何一个 IP 都能访问挂在它上面的任何网站**，决定访问哪个网站的是 SNI 和 Host，不是 IP。于是可以这样做：

> **连接的目标 IP 自己挑，SNI 照样写你的域名。**

这就是「优选 IP」：用测速工具（我用的是开源的 CloudflareSpeedTest）把几百个 IP 挨个测一遍，挑出从你家连过去**最快、最稳**的几个，写进订阅。

那香港、日本节点是怎么来的？社区里流传的「香港 IP、日本 IP」列表，其实大多是别人在香港、日本云服务器上架设的**中转机**，它们把收到的 443 端口流量原样转给 Cloudflare。流量从香港进入 Cloudflare，就落在**香港机房**，Worker 在香港运行，出口自然是香港 IP。

一句话：**入口 IP 决定落在哪个机房，机房决定出口在哪个国家。**

这也意味着两件事：

- 中转机是别人的，**随时会下线**，所以要定期重测；
- 流量是 TLS 加密的，中转机看不到内容，但**看得到你连的域名和流量大小**。介意的话，只用 Cloudflare 官方 IP。

## 五、PROXYIP：为什么有些网站要「再绕一道」

Cloudflare 为了防止流量兜圈子，**不允许 Worker 直接连接 Cloudflare 自己的 IP**。可 ChatGPT、Discord 这类网站本身就挂在 Cloudflare 上，Worker 连不过去。

解决办法是先连到一台墙外的普通服务器，由它代为转进去，这台服务器就叫 **PROXYIP**。edgetunnel 默认用的是作者提供的公共中转。YouTube、奈飞不在 Cloudflare 上，用不到它。

## 六、我踩过的坑

实际部署时遇到的几个问题，按出现顺序记下来：

1. **`workers.dev` 默认域名在国内被墙**，必须绑定自己的域名。绑之前先把域名的 DNS 托管到 Cloudflare。
2. **一定要用单独的 Cloudflare 账号。** Workers 跑代理违反 Cloudflare 服务条款，有封号风险。我的博客也托管在 Cloudflare 上，要是用同一个账号，封号会连博客一起带走。域名也要从旧账号迁到新账号：新账号添加站点，到注册商那里改 NS，生效后再从旧账号删掉。
3. **部署报错 `code: 10034`：邮箱没验证。** 老账号也可能从来没验证过邮箱，平时不影响使用，但用 Workers 时会被卡住。验证邮件死活收不到时，把账号邮箱换成另一个能正常收信的邮箱，再验证。
4. **`wrangler.toml` 里 `routes` 必须写在 `[[kv_namespaces]]` 之前。** TOML 的规则是，表头之后的字段都归属于这个表。写在后面的话，`routes` 会被当成 KV 表的字段，部署成功但域名根本没绑上，而且不报错。
5. **测速必须在直连状态下做。** 我的电脑常年挂着代理，所有流量都从境外绕一圈，在代理开着的情况下测出来的结果全都不准。但一关代理，我用来远程操作的工具也会断线。最后的办法是：**先把测速脚本放到后台，让它每隔几秒检测一次，发现已经切到直连再开始测。** 我关掉代理，等它跑完再打开。
6. **延迟最低的官方 IP 未必能用。** 我测到东京、新加坡机房的官方 IP，延迟只有 60 多毫秒，但访问我的 Worker 全部返回 403。Cloudflare 有些 IP 段专门服务它自家的产品，不承接普通网站流量。所以**测速之后，还要用 `curl --resolve 域名:443:IP` 确认这个 IP 真能访问到自己的 Worker。**
7. **挑脚本要看代码。** 我顺带看了另一个同类项目，发现订阅链接本身就等于管理权限（拿到订阅就能改配置、把你的流量转到别人的服务器），代码里还写死了一个来历不明的 IP。**这类脚本转发的是你全部的上网流量，自己审不了的代码，别跑。**

## 七、让它自己维护自己

中转 IP 经常失效，手动重测太麻烦。我把测速放到了家里的 NAS 上：它 24 小时开机，走的也是家宽直连。

- 每天凌晨 4 点跑一次：拉取候选列表、按地区测速、逐个确认能访问到 Worker、把结果写回订阅；
- **成功时不发通知，只在每周一发一条汇总**；可用节点太少或写回失败时，当天推送告警，并且不覆盖旧订阅；
- 写回订阅用的是 edgetunnel 后台自带的接口，拿管理密码登录，不需要额外申请 Cloudflare API Token。

订阅地址是固定的，每天换的只是它背后的节点。客户端需要时点一下「更新订阅」，拿到的就是当天最快的节点。

## 八、它能干什么，不能干什么

**免费额度**：流量不限，但**每天 10 万次请求**（北京时间早上 8 点清零），代理每新建一条连接算一次。家里看视频一天通常用几千次，够用。

**适合**：看 YouTube 这类视频网站、应急备用。

**不适合**：

- **ChatGPT、Claude 这类要登录的服务。** 出口 IP 今天在香港、明天在日本，而且是成千上万人共用的 Cloudflare IP，账号登录 IP 满世界跳，很容易被风控甚至封号。这类服务我只走自己那台固定 IP 的 VPS。
- **长时间大流量。** 服务条款明确禁止用免费服务大量转发视频流量，用得越狠，封号概率越高。好在账号是单独的，真被封了，换个账号、换个域名，半小时就能重新部署。

## 九、插曲：晚高峰卡顿，换 Hysteria2 就能解决吗？

搭完这条线的当晚，我在单位上网（电脑连着一部电信卡手机的热点，我自己的手机用移动流量），发现**两条线同时变卡**：自建 VPS 忽快忽慢，Workers 线路也不行。第一反应是「是不是搭 Workers 把什么搞坏了」。

按排障的老规矩，**先查证据，别急着下结论**：

- **服务器本身**：负载接近 0，网卡零错误，服务器直接下载能到 46 MB/s，没有问题；
- **有没有测试进程残留在偷带宽**：没有；
- **看连接本身**：在服务器上用 `ss -tin` 查我这边的 TCP 连接，**重传率 22.68%**，也就是服务器发给我的数据，每 100 个包丢了 20 多个。

当时的判断是：跟搭 Workers 无关，问题在**晚高峰的出国线路**（后面会看到，这个判断只对了一半）。国内视频不出国，从本地 CDN 机房就能拿到数据，所以一点不卡；国外视频要挤运营商的国际出口，晚上七点到十一点出口拥堵，就开始大量丢包。Workers 线路同样慢，还多一层原因：那批优选 IP 是按**家里宽带**测出来的，换到别的网络，线路完全不同，自然不灵。

网上普遍说，丢包严重就上 **Hysteria2**。它基于 UDP，丢包了只补发、不主动降速，而 TCP 一丢包就把速度砍半。我在 VPS 上装了一个 Hysteria2，用手机（移动 5G）打开 fast.com，在同一网络下对比：

| 协议 | 实测速度 |
|---|---|
| VLESS + Reality（TCP） | **240 Mbps** |
| Hysteria2（UDP） | 120 Mbps |

**Hysteria2 反而慢了一半。** 原因有两个：

1. **我的 VPS 早就开了 BBR 拥塞控制。** BBR 不把丢包当成拥堵信号，丢 20% 的包也能维持速度。「TCP 一丢包就砍半速度」说的是传统算法，开了 BBR 之后，Hysteria2 的优势就没了；
2. **运营商对 UDP 限速。** 手机流量这类网络经常对 UDP 做 QoS，Hysteria2 被压住了。

所以「Hysteria2 一定更快」**并不绝对**，要看服务器开没开 BBR、运营商限不限 UDP，**实测才算数**。最后我把 Hysteria2 留作备胎，主力还是 VLESS。

那丢包到底出在哪？我的 VPS 买的就是**三网回程 CN2 GIA** 的线路，按理说晚高峰不该这样。于是做了一组对照：**同一台服务器、同一时刻**，分别看发往家里宽带和发往单位手机 5G 的连接。

| | 家里宽带（电信） | 电脑连电信手机热点（电信 5G） | 手机流量（移动 5G） |
|---|---|---|---|
| 重传率 | **0.06%** | **20% 以上** | **0%** |

这里还有个插曲：我一开始把那个丢包严重的来源当成了「我的手机」，结论也写成了「手机 5G 丢包」。后来才想起来，我的手机用的是**移动**卡，而那个来源的 IP 查出来属于**电信**。翻了面板里各设备用过的 IP 记录，才对上号：丢包严重的是**连着电信手机热点的电脑**，我自己的手机用移动流量时一点不丢。**查到一个 IP，先确认它到底是哪台设备、走的什么网，别想当然。**

再用 `mtr` 从服务器追踪到这个电信 5G 出口的回程路由：跨太平洋那一段确实走的是 CN2 GIA（`59.43` 开头的节点），延迟稳定在 124 毫秒；进入国内后转进普通的 163 骨干网（`202.97` 开头），再进入电信的 5G 移动网络。

结论很清楚：**CN2 GIA 没问题，同一台服务器到家宽、到移动 5G 都几乎零丢包，只有晚高峰的电信 5G 这一段丢得厉害。** 这不是换一家 VPS 能解决的，电脑改连移动卡手机的热点就行。如果看到网上说「晚高峰卡就换 CN2 GIA」，先用这种对照法查清楚丢包在哪一段，免得花冤枉钱。

排查中还有一个小坑：一开始我在电脑上对比两个协议，Hysteria2 的数据差得离谱。查服务端日志发现，**客户端来源地址竟然是服务器自己**。原来电脑开着代理软件，Hysteria2 的 UDP 包被代理拦截，塞进现有的 VLESS 隧道绕了一圈，测的根本不是 Hysteria2。**测代理协议时，一定要确认测试流量没有被另一层代理套住。**

## 十、和自建 VPS 比一比

| | Cloudflare Workers | 自建 VPS（VLESS + Reality） |
|---|---|---|
| 伪装方式 | 躲在 Cloudflare 后面，看起来像访问一个普通小网站 | 握手时冒充大网站（如 amazon.com），像在逛购物网站 |
| 出口 IP | Cloudflare 共享 IP，不固定 | 自己独享，固定不变 |
| 被封风险 | 封 Cloudflare 代价太大，一般不会 | 单个 IP 理论上可能被封，但 Reality 很难识别 |
| 成本 | 免费，但违反服务条款 | 按月付费，合规 |
| 适合 | 看视频、备用线 | 日常主力、AI、要登录的账号 |

一句话总结：

> **Workers 方案是借大平台的掩护，让别人的机房替你出门；自建 VPS 是在墙外租一间自己的房子，门口挂上大网站的招牌。**

两条线互为备份，才是真的安心。
