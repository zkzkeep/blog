## 起因

[上一篇](/posts/apple-silicon-x86-windows-usb-passthrough/)讲了怎么在 M 系列 Mac 上用 UTM 跑一台 x86 Windows 7，把一个只有 Windows 客户端的加密 U 盘直通进去解锁，再把文件传回 Mac。

方案跑通之后用了两周，攒下三个不爽：

1. **解锁之后，加密区要等很久才出现**，而且感觉"以前没这么慢"
2. **进了 Windows 桌面，还得回 Mac 再点一次"连接 U 盘"**
3. 大文件照旧很慢

这次花了一整天，前后改了十几个版本。三个问题都有了着落，路上还学到一件比技术细节更重要的事：**我对同一个崩溃连着误判了三次**。下面按顺序讲。

## 一、加密区出现得慢：一个后台脚本，两个 bug

Windows 里常驻着一个我自己写的小脚本：盯着有没有 U 盘插进来，发现厂商客户端就自动启动它，等加密区出现再做后续动作。

问题出在它"盯"的方式。它**每 2 秒**用 WMI 查询一次所有磁盘，而这个查询会顺带读取**每个盘的剩余空间**：包括走 WebDAV 的网络盘（当时还处在"脱机"状态，每次都要等超时），也包括**刚解锁、正在挂载的加密区**。这台 Windows 只有一个模拟出来的 CPU 核，这个查询正好卡在"输完密码 → 加密区挂载"这一段，和系统抢同一个核。

改成只看"盘符表有没有变化"：这个调用不读介质、不走网络，几乎零开销。

顺手查出第二个 bug，比第一个更离谱：**这个脚本里的中文从来就没被正确读过。** Win7 自带的是 PowerShell 2.0，用 `-File` 运行一个**没有 BOM** 的脚本时，它按系统代码页（中文系统是 GBK）来读 UTF-8 文件，于是：

| 脚本里写的 | PowerShell 2.0 实际看到的 |
|---|---|
| `导出到Mac` | `瀵煎嚭鍒癕ac` |

所有按中文名找文件夹、认卷标的逻辑都在拿乱码做比较，永远匹配不上。它之前一直"能用"，纯属另一条兜底分支凑巧撑着。之后所有写给 Windows 的脚本统一加 BOM，单元测试也锁住了这一条。

还有个同类的坑：**PowerShell 会把中文弯引号 `“”` 当成普通双引号。** 在双引号字符串里写一句 `请运行“恢复默认设置”`，字符串就会提前结束、脚本直接语法错误。含中文引号的文字只能放在单引号字符串里。

另外顺手关掉了几项在单核模拟环境里特别伤的功能：自动播放（新盘一插上就扫描全部内容）、缩略图和文件夹类型识别（打开文件夹就把文件读一遍）、脱机文件、搜索索引、预读和实时扫描。这台虚拟机没有网卡，只做文件中转，关掉不影响用途。

结果：从客户端启动到加密区出现，含输入密码，稳定在 8 到 13 秒；读加密区根目录只要 0.1 秒。

## 二、去掉"第二次点击"：找到一个真正的就绪信号

上一篇说过，"进桌面后再点一次"没法自动化：Mac 这边分不清 Windows 是"停在登录界面等密码"还是"已经进了桌面"。当时试过用 CPU 占用率判断，结果在登录界面就误判了，还把 U 盘的直通搞断了。

这次换了个思路：**Windows"启动"文件夹里的程序，只有用户真正登录进桌面之后才会运行。**所以只要让启动项往共享目录里写一个"我已登录"的信号文件，Mac 看到它的修改时间晚于本次开机，就能确定桌面已经就绪，这时再自动接入 U 盘。这是一个因果上成立的信号，不是靠统计猜出来的。

加了两道保护：

- 每次登录只自动接入一次
- 这一次开机里如果已经接入过 U 盘，就不再自动接入，免得把正在使用的盘断开重连

第二道保护是踩坑之后才加上的：有一次 Windows 开着的时候我重启了 Mac 端的助手，它把 Windows 早先写的旧信号当成了新信号，把正在用的 U 盘断开又重连了一次，加密区被重新锁上。之后改成：助手启动时，已经存在的信号一律视为已处理。

## 三、把"36 秒"拆开看

去掉第二次点击之后，体感上从桌面出现到弹出密码框还要半分钟左右。与其凭感觉优化，不如先埋点计时，把每一段拆出来：

| 开机后 | 事件 | 这一段 |
|---|---|---|
| 第 17 秒 | 桌面出现 | |
| 第 27 秒 | 后台脚本开始运行 | 10 秒：启动项排队 + PowerShell 加载 |
| 第 43 秒 | 共享盘可用，发出登录信号 | **16 秒** |
| 第 45 秒 | Mac 收到信号，接入 U 盘 | 2 秒 |
| 第 52 秒 | Windows 认出 U 盘，启动客户端 | 7 秒 |
| 第 53 秒 | 密码框出现 | 1 秒 |

数字一摆出来，该改哪里就很清楚了：

- **最大的 16 秒在等共享盘可用。** Windows 的 WebDAV 客户端服务默认"有人访问才启动"，偏偏脚本检查不通后还要等 10 秒才再试。改为让这个服务随开机启动，检查间隔缩到 2 秒。
- **PowerShell 光加载就要 11 秒左右。**在启动项里另加一个极小的 cmd 脚本，一登录就先把信号发出去（cmd 几乎是瞬间启动的），让"Mac 接入 U 盘"和"PowerShell 慢慢加载"同时进行。这个 cmd 必须只用 ASCII 字符，原因和上面一样：cmd 按 GBK 读批处理文件。
- **Mac 端从每 5 秒检查一次信号，改成每秒检查一次**，只看一个文件的修改时间，开销可以忽略。

最后从桌面出现到弹出密码框，**36 秒降到约 25 秒**。剩下的"接入 U 盘 → Windows 认出设备"那几秒是模拟开销，压不下去。

## 四、两个一模一样的网络盘

有一阵子，"计算机"里出现了两个一模一样的共享盘，Y: 和 Z:。我写了去重逻辑：用 `net use` 列出所有映射，多余的删掉。结果完全没用。

让 Windows 把 `net use` 的原始输出吐出来一看：**里面只有 Y:，根本没有 Z:。**

原来 Z: 是 UTM 的 Guest Tools **以系统身份**挂上去的，"计算机"里看得见，但普通用户的 `net use` 列不出来。某次登录时 Z: 暂时连不上，脚本就以为盘符没人用，自己又映射了一个 Y:。去重逻辑只看 `net use`，在它眼里只有一个盘，当然认为没有重复。

改成直接检查每个网络盘能不能打开共享内容：Guest Tools 挂的那个能用，就用它，并删掉自己映射的；它暂时连不上时最多等一分钟，才考虑自己映射。

这件事还暴露了另一个问题：Windows 实际运行的是脚本在本地的一份**副本**，只有手动运行"优化并更新"时才会刷新。我在 Mac 上修好了脚本，Windows 里跑的却一直是旧的。后来让后台脚本每次登录时自己比对共享目录里的版本，有新版就自动更新并重启自己。

## 五、UTM 启动崩溃：三次误判

这是这篇最想记下来的部分。

### 现象

点"启动"之后，UTM 有时半天不动，去点它一下，就弹出"UTM 意外退出"；重新打开之后，又能正常启动。

### 第一个发现："两个 UTM"

程序坞里常常同时出现两个 UTM 图标。用 `lsappinfo` 抓到了原因：Mac 端助手用来查询虚拟机状态的，是 UTM 自带的命令行工具 `utmctl`，而它每次运行都会以**前台应用**的身份向系统登记（`type="Foreground"`），位置又在 UTM.app 里面，所以程序坞把它显示成了第二个 UTM。助手每 5 秒查一次状态，图标就一直在。

改为不用 `utmctl`：查状态直接看后台有没有这台虚拟机的 QEMU 进程，启动改用 AppleScript。图标问题解决了。

### 误判一："是 utmctl 抢了前台，导致 UTM 崩溃"

UTM 崩溃前的日志里总有一条 AppKit 断言：`[self canBecomeMainWindow]`。我的推理是：`utmctl` 以前台应用身份登记，抢走了"主窗口"的位置，UTM 想把虚拟机窗口设为主窗口时就失败了。逻辑很顺。

**被证伪：**改用 AppleScript 启动、完全不调用 `utmctl` 之后，同样的断言照样出现。

### 顺藤摸瓜：崩溃为什么会连带"写不进共享盘"

崩溃报告的时间，和每一次启动失败一一对得上。更要紧的是，每次 UTM 崩溃之后，那一轮开机里 Windows 往共享盘写文件全部失败，右下角弹出"延缓写入失败"，登录信号自然也发不出去，于是又得手动点一次。

链条是这样的：UTM 崩溃 → 重试时 UTM 被重新拉起 → **新的 UTM 进程没有登记共享目录** → 共享盘能读不能写。修法是虚拟机确认起来之后，再登记一次共享目录。这一环修好之后，就算 UTM 崩了，后面的流程也不受影响。

但崩溃本身还在。

### 误判二："是启动前同步中转盘引起的"

这时候我心里清楚一点：以前没有这个问题，是这一轮改动带进来的。回头翻，每次启动失败的前一刻，助手都刚把"中转盘"镜像挂到 Mac 上同步过一次（中转盘下一节讲），而这个镜像文件就放在 UTM 的虚拟机包里。推测是包里的文件一变，UTM 重新加载虚拟机，正好撞上启动。

去掉启动前的同步之后，**又崩了一次**。被证伪。

### 最后：老老实实逐次对照

两次都是"找到一个说得通的原因就动手"。这次换个做法：把当天每一次启动都列出来，看每次启动前几秒，助手都做了什么。

| 启动前 2 到 17 秒内，是否用 AppleScript 查询过虚拟机列表 | 结果 |
|---|---|
| 查询过（6 次） | **6 次全部崩溃** |
| 没有查询（5 次） | **5 次全部成功** |

这个查询由界面上的"刷新状态"按钮触发，它会通过 AppleScript 把 UTM 拉起来，并逐个读取虚拟机配置。而人为什么总在启动前点"刷新状态"？因为另一个界面问题：UTM 没开的时候，助手查不到状态，Windows 那张卡片就显示"待检查"，看起来像要先刷新一下。

修法：助手平时**完全不再向 UTM 查询虚拟机列表**，改为直接读硬盘上的虚拟机配置文件，状态看进程。此后再没崩过。

### 这一段的教训

- 前两次误判都是**"时间上相关 + 机制上说得通"**，就当成了原因。两个都经不起一次反例。真正站得住的，是 6 比 0 对 5 比 0 这种对照。
- "以前没有这个问题"这种直觉，**方向是对的**，但它只能告诉你"去找这一轮的改动"，指不出是哪一个改动。第二次误判就是把直觉当成了答案。
- 崩溃栈里那段 SwiftUI 调用（在检查"是否在主线程"时崩溃），两周前就在 UTM 退出时出现过。所以 UTM 本身确实有这个 bug，但它什么时候被触发，取决于我们怎么调用它。

## 六、中转盘：一个被我测错两次的速度

大文件慢的问题，这次试了"中转盘"：给虚拟机多挂一块虚拟硬盘，Windows 里显示为 T:。Windows 把文件复制到 T:，关机后 Mac 再把镜像挂起来取走文件。

挂盘本身就踩了一个坑：这台虚拟机用的是老式 PC 主板，**只有两条 IDE 总线**，已经被系统盘和光驱占满。UTM 把第三块 IDE 盘排到了不存在的第三条总线上，QEMU 报 `Bus 'ide.2' not found` 直接退出，而 UTM 界面上只显示一句"尝试连接到 SPICE 服务器时出现内部错误"。改成 USB 接口的虚拟硬盘之后才正常。

速度测了三轮，前两轮的结论都是错的：

| 轮次 | 测法 | 结论 | 问题出在哪 |
|---|---|---|---|
| 第一轮 | T: 实测 2.2 MB/s，对比两周前测的共享盘 264 KB/s | 中转盘快 8 倍 | 共享盘的数字是**优化之前**测的，没有重测 |
| 第二轮 | 同一批文件先复制到 T:，再复制到共享盘，共享盘到了 3 MB/s | 共享盘反超，中转盘可以拆了 | 第二次复制时文件还在 Windows 内存缓存里，**根本没从 U 盘读** |
| 第三轮 | 用没复制过的文件，按文件落到 Mac 的时间逐个算 | T: 约 2.2 MB/s，共享盘约 1.35 MB/s | 这次才是公平的 |

所以中转盘保留，而且还能再讲出一个原因：共享盘走 WebDAV，协议开销被模拟放大；中转盘是本地磁盘读写，即使和 U 盘挤在同一个模拟 USB 控制器上，也仍然更快。共享盘也比两周前快了 5 倍左右，这是第一节那批 Windows 调优的功劳。

两个测速的规矩记下来：

- **测速用没碰过的数据**，否则测的是缓存
- **别信 Windows 复制窗口上的速度和剩余时间**，在网络盘上尤其不准（显示"剩余 1 小时"的一批文件，实际两分半钟就传完了）。以文件真正落到目标端的时间为准

最后，往 U 盘里**写**始终只有 1 MB/s 左右，和数据从哪来无关。这是模拟 USB 写入的上限，换更快的 U 盘也没用。

## 七、小事一件：关机时别再问我

Windows 关机时常常弹出"还需要关闭 N 个程序 / 强制关机"，挡住关机的是正在锁盘的厂商客户端。对这个工具来说，点"安全退出"就代表事情做完了，所以打开了 Windows 自带的"关机时自动结束程序"（`AutoEndTasks`，最多等 3 秒）。它仍然是 Windows 正常关机，已经写好的数据照常落盘，只是不再停下来问。

## 结论

现在的体验是：

1. 插上 U 盘，点一次"启动"
2. 大约 25 秒后密码框自动弹出，输完密码，加密区自动打开
3. 文件复制到 T:，点"安全退出"，Windows 自动关机，文件自动出现在 Mac 上

性能的天花板没变，**根因还是"在 ARM 上逐条翻译 x86"**。想再往上走，只能换成原生 ARM 的系统，只让厂商客户端那一个进程走模拟。那是下一篇的事了。

这一天最大的收获不在技术细节，而在方法：

- **没有对照的因果都是猜测。**"它们总是一起出现"不等于"一个导致另一个"
- **测量之前先确认测量本身是对的**：基准有没有过期，数据是不是冷的，看的数字是不是真实到达的
- **从另一台机器看不见的地方，就让它自己留日志。**这一轮能把问题一个个钉死，靠的是 Windows 和 Mac 两边各自写下的时间线
- **听到"以前没这个问题"，先别解释，去找差异。**这次顺着这句话，才把目光从 UTM 本身挪回到自己的调用方式上
