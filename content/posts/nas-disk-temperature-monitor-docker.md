## 为什么不只看 DSM，而要做这个 Docker

这台群晖有 6 块 SATA 机械盘组成 RAID 5，还有 2 块 NVMe。夏天机械盘通常在 40°C 左右，并没有出现故障；做这个监控器不是因为已经过热，而是为了补足三个实际缺口：

1. **不能一眼总览。** 我需要同时看 8 块盘的温度，而不是逐块进入 DSM 存储管理器翻 SMART 页面。
2. **没有明确的自动处理链路。** 想要的规则是：机械盘到 50°C、NVMe 到 65°C 时立刻提醒；若连续 10 分钟仍高温，停止高 I/O 的下载、做种和音乐服务，先给硬盘降负载。
3. **要能在外面安全查看。** 页面经 Cloudflare Tunnel 暴露，再由 Cloudflare Access 保护；这样能随时查看，但不把硬盘信息裸露在公网。

Docker 只是承载方式，不是目的。它让监控逻辑、网页、SMART 工具和告警逻辑装在一起，同时通过只允许的 Docker 容器名执行保护动作。监控器每分钟采样一次，低于阈值为正常；首次超温立即发企业微信；连续超温满 10 分钟才停止 qBittorrent、Transmission 和 Navidrome。温度恢复后**不自动重启**，避免温度在临界点来回波动时又把负载顶上去，恢复服务由人工确认后执行。

## 过程记录：先把“看起来正常”的风险找出来

### 第一次失误：没读到温度，页面却显示绿色

初版页面里，部分盘只有破折号，没有温度值，但卡片仍是绿色。这个错误的原因是把“`smartctl` 命令有返回”误认为“已经拿到了温度”。实际并非如此：SMART 可以有响应，却没有可供解析的温度属性。

这类监控最怕的是假正常。于是状态被明确拆成三类：

| 情况 | 页面状态 | 含义 |
| --- | --- | --- |
| 能读取温度且低于阈值 | 绿色 | 正常 |
| 温度达到阈值 | 红色 | 已告警，并开始计算持续时间 |
| SMART 有响应但没有可识别温度 | 黄色“待核实” | 采集链路没有完成，不能当正常 |

**为什么要特别记录这一点：** 面板颜色不是装饰。对监控系统来说，缺数据应被视为观测异常；如果把它涂绿，正好会掩盖最需要排查的问题。

### 第二次排障：同类 SATA 盘为什么有的能读、有的不能读

接着发现，几块同一系列的 SATA 盘可以显示温度，另几块却只有 SMART 标题，没有属性表。最初把原因猜成 JSON 字段或正则解析差异，这是一次没有证据的判断；改解析器不能解决“底层没返回属性表”的问题。

随后直接在监控容器内查看各设备的原始 SMART 输出，并加上不唤醒待机盘的参数：

```bash
smartctl -n standby -d sat -A /dev/sata3
```

六块 SATA 盘都返回了完整属性表，温度属性也都存在；这排除了“硬盘休眠所以读不到”的猜测。关键差异在 `-d sat`：容器中的 `smartctl` 对群晖提供的 `/dev/sataN` 设备自动识别并不稳定。未显式指定协议时，部分盘得到空表；按 SAT 协议读取后，所有 SATA 盘稳定给出温度。

因此 SATA 的命令固定使用 `-d sat`，而不是继续调整温度字段的解析规则。

**容易错的地方：** 先确认原始命令到底返回了什么，再改解析代码。否则是在给错误的前提打补丁。

### 第三次失误：修复 SATA 时，误伤了 NVMe

把 `-d sat` 加进命令后，SATA 的温度都恢复了；但此前正常的两块 NVMe 又变成“待核实”。原因是我把 SATA 的传输层参数当成了通用参数，套给了所有设备。NVMe 是原生协议，不能带 `-d sat`。

最终改为按设备类型构造命令：

```python
def smartctl_command(device: str, *options: str) -> list[str]:
    transport = ["-d", "sat"] if Path(device).name.startswith("sata") else []
    return ["smartctl", *transport, *options, device]
```

并为两种设备分别做了断言：SATA 必须带 `-d sat`，NVMe 必须不带。重新构建容器后，6 块 SATA 和 2 块 NVMe 均重新显示温度。

**这次错误的教训：** “让一类设备工作”的修复不能默认适用于另一类设备。协议边界应该在命令构造处显式表达，也要有最小的回归检查，而不是改完只看一半盘恢复了就结束。

## 保护链路如何验证，而不止是写在代码里

到这里，读温度只是第一步。还需要分别验证“告警真的能到”和“高温时真的能减载”。

1. 单独调用企业微信发送函数，确认手机实际收到测试告警。
2. 在明确授权后，实际调用保护函数。它只允许停止固定的三个容器：qBittorrent、Transmission、Navidrome，避免误操作其他服务。
3. 用容器状态再次核对：三个服务从 `running` 变为 `exited`；随后人工启动，三者都恢复 `running`。

这里把“首次高温提醒”和“持续十分钟后停服”分开，是为了避免一次瞬时高温就中断服务；而把“自动停止”和“手动恢复”分开，是为了避免程序自行恢复高负载。

## 最终状态与后续原则

目前 8 块盘都能读取温度；一次夏季采样中，机械盘为 39到41°C，两块 NVMe 为 39°C 和 48°C，均低于阈值。页面可以通过受 Access 保护的地址查看。

这次小项目最值得留下的不是 Docker 文件，而是以下几条做法：

- 先说明为什么监控、阈值和保护动作这样设计；
- 没有温度值时，明确标为“待核实”，绝不以绿色掩盖；
- 用原始 SMART 输出验证问题在采集层还是解析层；
- SATA 与 NVMe 分别处理，并在一次改动后检查两类设备；
- 告警和停服都要真实演练，代码存在不等于链路可用。

监控平时显示“正常”并不难；难的是遇到异常时，能够分辨它是在报警、在缺数据，还是已经真正完成了保护动作。
