> 文中域名、内网地址、序列号和企业微信配置均已脱敏；命令思路可直接复用。

我这台群晖有 6 块 SATA 机械盘组成 RAID 5，另有 2 块 NVMe 做缓存和 Docker 盘。夏天机械盘平时大约 40°C 上下，温度本身并不吓人；真正让我不踏实的是：DSM 的界面看状态很方便，却没有一眼能看全每块盘温度、留历史、超温后立即告警的地方。

于是做了一个很小的 Docker 监控器：每分钟读一次 SMART，网页展示 8 块盘温度；机械盘到 50°C 立即通知，持续 10 分钟则停止下载、做种和音乐播放服务，给硬盘减载。

这听着像半天能收工的小活。实际踩了三次坑，最后的收获反倒不在 Docker，而在一句老话：**监控不是“页面有数字”就算完成，必须把每一条验证路径走到终点。**

## 目标先说清

我定的规则很简单：

- 6 块 SATA 机械盘：50°C 进入异常；
- 2 块 NVMe：65°C 进入异常——NVMe 正常工作温度比机械盘高，不能机械套 50°C；
- 首次超温：立即推送企业微信；
- 连续超温 10 分钟：停止 qBittorrent、Transmission 和 Navidrome；
- 温度恢复后**不自动恢复服务**，人工确认散热正常再启动。

最后一点是刻意为之。自动停、自动开会在温度阈值附近来回抖；对保种和媒体服务来说，宁可让我手动确认，也别让程序自作主张把负载重新顶上去。

## 第一坑：温度没读到，却被画成了绿色

第一版面板里，几块盘没有温度，只显示一个破折号；但卡片还是绿色。接口没报错，页面也“好看”，这是最危险的一种假正常。

根因很朴素：SMART 命令成功返回，不等于其中一定有可识别的温度字段。

我把逻辑改成了三态：

| 状态 | 面板颜色 | 处理 |
| --- | --- | --- |
| 温度低于阈值 | 绿色 | 正常 |
| 温度达到阈值 | 红色 | 告警并开始计时 |
| SMART 没有可识别温度 | 黄色 | 明确显示“待核实”，不把它伪装成正常 |

这条改动看似只是 UI，实际上是监控系统的底线：**缺观测值必须是故障状态，不是成功状态。**

## 第二坑：同一型号 SATA 盘，为什么有的能读、有的读不到？

6 块机械盘是同一系列企业盘。奇怪的是，部分盘能读到温度，部分盘只返回 SMART 标题，没有属性表。

一开始我猜是 JSON 字段格式不同，连续改了解析器两次，没解决。后来不再猜，直接进入运行中的容器，读取原始输出：

```bash
for d in /dev/sata1 /dev/sata2 /dev/sata3 /dev/sata4 /dev/sata5 /dev/sata6; do
  smartctl -n standby -d sat -A "$d"
done
```

`-n standby` 的作用是：如果盘真的处于待机状态，直接报告而不把它唤醒。结果 6 块盘全部正常返回完整 SMART 表、退出码均为 0——不是休眠。

关键在 `-d sat`。

容器里的 `smartctl 7.5` 对群晖的 `/dev/sataN` 自动协议识别并不一致：不显式指定时，有些盘能读，有些盘拿到空表；强制按 SAT 协议读取后，6 块盘都稳定返回 ID 194 的 `Temperature_Celsius` 属性。

所以 SATA 的读取命令固定为：

```bash
smartctl -d sat -i -A -j /dev/sata3
```

不是“换一个解析正则”就能解决，前提是底层真的把属性表拿回来了。

## 第三坑：修好了 SATA，又把 NVMe 修坏了

这次是我自己制造的回归。

既然 SATA 要强制 `-d sat`，我图省事把这个参数套进了所有设备的命令。机械盘全好了，两块 NVMe 却立刻变成“待核实”。

原因也很直接：`-d sat` 是 SATA/SAT 传输层参数，NVMe 有自己的原生协议，不能混用。

最终把命令构造收敛成一个单独函数，并给两类设备各写了一条断言：

```python
def smartctl_command(device: str, *options: str) -> list[str]:
    transport = ["-d", "sat"] if Path(device).name.startswith("sata") else []
    return ["smartctl", *transport, *options, device]

assert smartctl_command("/dev/sata3", "-A") == [
    "smartctl", "-d", "sat", "-A", "/dev/sata3"
]
assert smartctl_command("/dev/nvme0n1", "-A") == [
    "smartctl", "-A", "/dev/nvme0n1"
]
```

这种“按设备类型分流”的代码比一句漂亮的通用命令笨一点，却不会为了修 SATA 伤到 NVMe。

## 现在的读取结果

最终 8 块盘都能读到温度和型号。一次夏季采样中，机械盘在 39–41°C，NVMe 在 39°C 和 48°C；都在设定阈值之下。

这说明两件事：机箱风道目前没问题；监控器已经真正覆盖到了要监视的每一块物理盘，而不是只覆盖“恰好能自动识别”的那几块。

## 告警和保护，不做“理论上可以”

温度页面放在 Cloudflare Tunnel 后面，再加 Cloudflare Access。这样可以在外面随时看，但不把硬盘型号、序列号和运行状态裸露在公网。

告警测试没有伪造温度，只单独调用企业微信通知函数；手机确实收到了测试消息。

更重要的是，保护动作也做了真实测试。监控器内的保护函数只允许操作固定的三个容器名：

```python
PROTECT_CONTAINERS = ("qbittorrent", "transmission", "navidrome")
```

在明确授权后，实际调用了保护函数，三个服务均由 `running` 变为 `exited`；随后手动恢复，三者都重新回到 `running`。这一步比“代码里写了 `docker stop`”有价值多了——它证明了容器持有的 Docker 权限、容器名和停服路径全都是真的。

## 最后的教训

这套小监控真正留下的不是一页温度卡片，而是几条以后还会继续管用的规矩：

1. **没有数据不等于正常。** 面板必须把缺数据显眼地标出来。
2. **先看原始输出，再写解析器。** 连续修改正则，只是在给猜测打补丁。
3. **不同设备类型要有明确边界。** SATA 的补丁不该碰 NVMe。
4. **自动保护必须真测。** 告警能到、服务真能停、服务能恢复，三件事缺一不可。

监控的价值不在于它平时说“都很好”，而在异常时你敢相信它说的话，也敢相信它会做该做的事。
