周日傍晚，我想打开家里的 Emby 看点东西，浏览器却甩给我一个 **Cloudflare Error 1033 — Tunnel error**。

一个错误页，牵出一整晚的排障、一次彻底的服务迁移，最后以我把一块固态硬盘从 NAS 里拔出来收尾。记下来，既是复盘，也给同样在家折腾 NAS 的人提个醒。

## 一、第一现场：不是 Emby 的错

1033 是 Cloudflare Tunnel 的错误——**问题不在 Emby，而在"隧道的另一头连不上了"**。我打开内网的群晖，Container Manager 里一看：十几个容器全是灰点（已停止），只有 immich 的一个还亮着绿灯，写着"已运行 6 小时"。

"只有一个还活着、其余全停"——这个模式很关键。它后来成了整条线索的锚点。

## 二、排障：先把假设一个个证伪

家里 NAS 出问题，最容易的反应是"重启一下试试"。但重启会毁掉现场，也可能把真正的原因永远盖住。所以我逼自己按纪律来：**先提假设，再找能证伪它的证据，别用"症状吻合"直接定罪。**

**假设一：NAS 重启过，容器没跟着自启。**

一条命令就否了：

```
$ uptime
 up 37 days, ...
```

开机 37 天，根本没重启。假设一出局。

**那是什么时候、以什么方式停的？**

我去翻各个容器数据目录的修改时间，发现一批配置和数据库文件都停在**同一分钟**——今早 7 点零几分。而且它们是"干净落盘"的（比如 Transmission 只有在正常退出时才会重写它的配置文件）。也就是说：**这些容器是在早上 7 点被"优雅地停止"了，不是崩溃。**

immich 那个"已运行 6 小时"，正好对得上 7 点这个时间点——它是唯一自己爬回来的。

**假设二：是我那个"磁盘温度守护"容器把它们停了。**

我之前写过一个小容器，逻辑是"某块盘持续超温就停掉几个吃硬盘的服务保护一下"。看着像是它干的。但翻它的日志，只有早上 7 点零几分的**一条温度告警**，没有任何"执行保护、停止服务"的记录。按它的逻辑，要"持续超温十分钟"才会动手停容器——而它自己在报警几秒后就跟着一起被停了，**根本没来得及执行**。它是受害者，不是凶手。假设二也出局。

## 三、真相：所有鸡蛋，放在一个会发烫的篮子里

那条温度告警指向了根子：**我 NAS 上所有 Docker 数据，都单独放在一块廉价消费级 NVMe 固态上，没有任何冗余，而这块盘早上 7 点冲到了 67°C。**

更巧的是，我机器里还有另一块牌子好一点的 NVMe，同一时刻只有 40°C，凉快得很，而且几乎是空的。**同样的机箱、同样的风道，两块盘差了将近 30°C——这说明发烫的那块，是盘自己的问题（廉价主控、散热差）。**

到这里，"为什么全站只有 immich 自己回来了"也有了答案，这是一个值得记住的冷知识：

- Docker 的重启策略里，`restart: unless-stopped` 的含义是——**如果容器是在"已停止"状态下遇到守护进程重启，它不会被自动拉起。**
- 而 `restart: always` 是**无条件拉起**。

我大部分服务写的是 `unless-stopped`，immich 恰好写的是 `always`。那天早上容器被整体停掉后，只有 `always` 的 immich 无条件复活，其余全都躺在"已停止"里没人管，一躺就是六个小时。

## 四、治本：把服务从烫盘上搬走

止血很简单，把重启策略统一改成 `always`，服务先回来。但这只是让它下次能自愈，没解决"盘会烫"这个根子。

真正的方案是：**把整套 Docker 从那块会过热的廉价盘，搬到凉快、空旷、更靠谱的那块盘上。**

这件事分两层，很多人会踩的坑就在这——只搬一半：

1. **各服务的配置和数据库**（bind 挂载的那部分）——改改路径、拷过去就行。
2. **Docker 引擎自己的镜像层、容器读写层**——这层藏在系统目录里，改配置文件根本碰不到，它是跟着"Container Manager 装在哪个卷"定死的。

只搬第一层，那块盘照样在写、照样发烫。所以要彻底，就得连 Container Manager 套件本身一起迁到新卷。

群晖套件没法"原地换卷"，只能卸载重装。而重装会重新拉取全部镜像——十几个 G，走国内镜像源慢得让人肉疼，中途卡住还会拖长停机。我的办法是：**先把所有镜像 `docker save` 导成一个 tar 存到大容量的机械盘阵列上，卸载重装后再 `docker load` 导回来，全程不联网、不重拉。** 停机时间从"看老天爷脸色"变成可控的几分钟。

## 五、一个自己给自己挖的坑：看不见的悬空软链

迁移基本顺利，但重装后公网访问全线 530（隧道又不通了）。排查发现：**内网服务全好，是 Cloudflare 隧道容器起不来。**

翻它日志，一直在报"缺少隧道 ID"死循环重启。根子是它读不到隧道令牌。再往下挖——它读令牌靠一个符号链接（软链），指向一个共享配置文件；而我在迁移中给共享文件改名后，**这个软链就悬空了**，令牌读成了空。

为什么之前没发现？因为这几个服务的目录是 root 私有权限，我平时用的普通账号**根本看不到里面有这么个软链**，一路误判"这里没有配置"。等把旧目录一改名，悬空才暴露出来。

教训很直白：**批量修软链这种事，得用管理员权限把所有目录扫一遍，别信普通账号 `ls` 出来的结果——它看不见的，不代表不存在。** 把软链重新指对、重建容器，隧道立刻连上，公网恢复。

## 六、拔盘惊魂：差点把自己锁在门外

服务全绿之后，我做了个决定：**这块烫盘既然空出来了，干脆拆下来给别人，家里留一块好盘就够了。**

但拔盘前得把盘上剩的东西全搬空。这里差点出大事——盘上还压着两样**要命的东西**：

- **我远程进 NAS 的 Tailscale**，套件就装在这块盘上；
- **用户家目录**，里面藏着我 SSH 免密登录用的公钥。

这两样任何一个没安置好就拔盘，我就会**当场失联，半途卡死**——而且家里那条内网直连，恰好因为我 Mac 上代理软件的配置，是不通的，唯一的路就是 Tailscale。

好在处理得当：Tailscale 重装到了新卷、还保住了原来的地址；家目录用群晖共享文件夹的"换卷"功能整个迁到了有冗余的阵列上，SSH 公钥毫发无损地跟着过去了。搬之前我还特意把公钥内容在本地存了一份——它其实能从我手里的私钥重新算出来，真丢了也能补回去，不至于锁死。安全网先铺好，再动手。

最后进存储管理器删掉那块盘的存储空间，关机、拔盘、开机。回来一看：Docker、Tailscale、所有服务全部自动归位，公网也通。**那块单点、廉价、会过热的盘，连着它带来的病根，一起被我拆走了。**

## 七、复盘：几条留给自己的规矩

- **别把所有服务的命，押在一块没有冗余的廉价盘上。** 便宜的消费级固态，主控和散热真的会出问题，而"单点"意味着它一出事就是全线。
- **排障先证伪，别顺着"看着像"下结论。** "以为重启了"被 uptime 一秒否掉，"以为是温度守护干的"被它自己的日志洗清——这两步要是省了，我大概率会修错方向。
- **`restart: always` 和 `unless-stopped` 的区别，关键时刻是六小时空窗和几秒自愈的差别。** 家里要长期在线的服务，我现在一律 `always`。
- **权限看不见的东西，不代表不存在。** 那个悬空软链就是活教训。
- **动任何"承载着你远程访问命脉"的东西之前，先确认还有另一条路能进去，或者先铺好安全网。** 差一点，我就把自己关在了门外。

一个 Emby 打不开的傍晚，最后变成了一次挺彻底的家底整理。折腾是折腾，但心里踏实多了——至少现在，我知道我的鸡蛋，没再全放在那只会发烫的篮子里。
